# AI 求职助手：竞品与付费验证方案

整理日期：2026-10-29。

## 1. 结论与切入点

先验证一款面向有经验求职者的付费工具：根据简历和求职要求，持续发现值得投递的岗位，说明匹配依据，并记录求职进度。

第一版只支持 BOSS，做好完整流程后再扩展第二个平台。优先服务研发、产品、数据等岗位中的一个细分人群，通过种子用户反馈选择，不同时覆盖所有职业。

不把“批量投递更多”作为唯一卖点。付费价值集中在：少看无关 JD、少重复操作、不错过合适机会、知道每个岗位处理到了哪一步。

## 3. 第一版做到什么

### 必须形成的使用流程

导入简历 → 设置求职条件 → 收集候选岗位 → 去重和规则过滤 → 补全 JD → AI 匹配 → 排序查看 → 沟通及进度记录。

- **简历画像**：提取技能、项目经历、年限、目标方向与硬性要求，允许用户确认和修改。
- **持续收集**：先在 BOSS 内支持搜索词、翻页与补充候选，保留职位来源、链接、完整 JD 和采集时间。
- **匹配解释**：提供分数、简历与 JD 对应的证据、能力缺口、待确认条件；不把分数解释为录用概率。
- **目标数量**：按“合格且去重的岗位数”计算，与每日沟通上限分开。达到目标、来源耗尽或预算耗尽时停止，并说明缺口。
- **任务与记录**：支持暂停、恢复、错误提示；区分已收藏、已沟通、简历已提交、结果待核实，允许用户核对。
- **用量统计**：记录分析次数、模型输入输出 token、耗时、失败次数，支撑成本核算和额度管理。

### 成本控制与交付边界

- 先执行城市、薪资、岗位方向等规则过滤，再调用 AI；复用简历摘要，控制返回理由长度。
- 缓存分析结果；简历、筛选标准或 JD 变化后才重新分析。
- 限制每次任务的候选数、AI 次数、耗时和预算；不承诺无限搜索或一定找到指定数量。
- 先保留现有沟通能力，不把无人值守自动投递作为首轮收费验证的前提。
- 暂缓多平台、自动回复、邮件发送、翻译、面试辅导等扩展功能。

## 4. 首轮收费方案

以下是待验证的试验方案，不是已验证的市场定价。

| 方案 | 建议权益 | 目的 |
| --- | --- | --- |
| 免费体验 | 首次 30 次岗位分析，可查看完整匹配依据和记录 | 让用户先判断结果是否有用 |
| 30 天试售包 | ¥29.9，含 1,000 次岗位分析，BOSS 单平台 | 验证真实付款、使用频率和单用户成本 |

- 暂不自动续费，不提供终身无限 AI，不承诺 offer 或面试数量。
- 一次分析定义为：成功生成并保存一份有效匹配结果。系统失败、格式无效及未变化的缓存结果不重复扣额度；低分结果仍算一次有效分析。
- 到期后停止新增付费分析，已生成记录继续可查看和导出。
- 模型由产品提供，避免普通用户自行配置 API Key。正式试售前确定退款规则，并在付款前明确展示。
- 先测试一个付费套餐，拿到数据后再决定是否增加 90 天包、额外分析包或多平台档位。

## 5. 怎么判断值得继续投入

招募 20～30 位正在求职、职业方向相近的种子用户。先观察他们如何选择岗位，再提供体验与付费入口；记录付款人数，不用“愿意购买”的口头反馈替代付款。

| 指标 | 首轮记录方式 | 判断用途 |
| --- | --- | --- |
| 匹配质量 | 用户标注推荐前 20 个岗位中多少个值得投，记录误判原因 | 以至少 14/20 为初始改进目标，不作为对外承诺 |
| 真实付费 | 争取首批 10 位真实付款用户，记录试用、付款、退款人数 | 验证价值是否足以支撑 ¥29.9 试售价 |
| 持续使用 | 记录首周是否再次搜索、查看推荐或更新进度 | 判断产品是否进入实际求职流程 |
| 运行稳定性 | 统计 JD 获取失败、任务中断、重复记录和恢复结果 | 确定平台维护与售后负担 |
| 单用户成本 | 记录模型、基础设施、支付退款、客服时间与获客费用 | 判断扩大规模是否划算 |

计算口径：

- 单用户贡献 = 实收收入 − 模型与基础设施变动成本 − 支付及退款损耗 − 变动客服成本 − 获客成本。
- 固定开发维护、税费等另计；token 便宜不代表整体盈利。
- 100 位用户各付 ¥29.9，流水为 ¥2,990，不是利润。
- 如果匹配质量差，先修评估与搜索；如果安装和异常处理大量依赖人工，先改善交付；如果使用频繁却没人付款，重新检验价值和价格，再扩展平台。

## 6. 商业发布前核清的事项

- **项目授权**：当前根目录 `LICENSE` 为 MIT，`README.md` 却写有“禁止用于商业用途”。核清所用版本、代码和素材的授权范围，必要时向原作者澄清或进行专业复核；不能直接把两处冲突视为已经解决。
- **平台边界**：分别确认数据获取、自动操作及商业使用的适用规则；竞品在销售不代表我们获得了平台许可。不以绕过验证或平台限制作为交付前提。
- **数据处理**：明确哪些简历和 JD 内容会发给模型服务，提供删除与导出能力，不向用户宣称数据完全不离开本机。
- **收费交付**：完成订单、付款核验、服务端额度账本、用量查询及退款处理；收费额度不能只依赖可修改的插件本地配置。

建议顺序：核清授权与平台边界 → 确定细分用户 → 完成 BOSS 匹配闭环 → 免费体验 → 小规模付费试售 → 根据质量、成本和付款数据决定是否接入第二个平台。
